# 高光谱设备目录监听接入服务设计方案

## 1. 背景与目标

当前后端已经具备通过上传 `.dat` 文件进行高光谱数据解析与成分预测的能力，核心入口是现有的 `predict` 接口，内部已经完成：

- 高光谱文件读取
- 光谱预处理
- 模型推理
- 结果结构化返回

现在希望新增一个后端服务，用于支持以下业务链路：

1. 通过 USB 线连接高光谱设备与移动设备
2. 将高光谱设备的存储目录挂载到移动设备或宿主系统可访问路径
3. 后端服务监听挂载目录中的数据变化
4. 发现新高光谱数据后自动触发解析与预测
5. 将任务状态和预测结果推送给前端

这意味着系统需要从“前端主动上传文件”扩展为“设备目录事件驱动的数据接入模式”。

本文档仅输出设计方案，不落地代码。

## 2. 建设目标

新增服务需要满足以下目标：

- 支持目录挂载后的自动发现，无需用户手工上传文件
- 尽量复用现有光谱处理和模型推理能力，避免重复实现
- 能够将“发现文件、处理文件、输出结果”的过程以状态流形式暴露给前端
- 能处理设备断开、文件写入未完成、重复扫描、异常文件等场景
- 方便后续扩展为多设备、多目录、多任务的采集接入架构

## 3. 适用前提

该方案成立的前提是：

- 高光谱设备以 USB 大容量存储、MTP 映射目录、厂商同步目录，或其他“可被宿主系统读取的文件目录”形式暴露数据
- 宿主环境能够访问该目录
- 写入完成后的数据文件格式仍然是当前系统可解析的格式，或可以通过新增适配层转换为当前解析流程支持的格式

如果设备不是以文件系统形式暴露，而是以串口、SDK、专有驱动、ADB 通道、网络接口输出数据，则目录监听不是最终方案，需要改成设备协议接入方案。

## 4. 推荐架构

推荐新增一个“设备接入服务层”，作为现有预测服务之前的上游输入模块。

### 4.1 架构分层

建议拆分为以下逻辑层：

1. 设备挂载层
2. 目录监听层
3. 文件就绪判定层
4. 任务编排层
5. 光谱解析与预测层
6. 结果推送层
7. 任务记录与审计层

### 4.2 数据流

完整链路建议如下：

1. 移动设备通过 USB 连接高光谱设备
2. 高光谱设备存储目录被挂载到指定路径
3. 后端服务监听该路径下的新增或变更事件
4. 服务检测到新文件后，先进入“待确认”状态
5. 当文件大小稳定、修改时间稳定、配套文件齐全后，判定为“可处理”
6. 任务编排器创建一个采集任务
7. 任务调用现有光谱处理逻辑和模型推理逻辑
8. 将结果写入任务记录
9. 通过轮询接口或 WebSocket/SSE 推送给前端

### 4.3 与现有系统的关系

当前系统已有能力适合被复用，而不是重写：

- `app/services/spectrum_service.py`：可继续承担文件解析与预处理职责
- `app/services/model_service.py`：可继续承担模型推理职责
- `app/routers/predict.py`：当前是 HTTP 上传入口，未来可以保留，同时新增“目录监听任务入口”

建议将“上传文件预测”和“目录自动发现预测”收敛到同一套内部业务服务，例如统一到一个“样本处理服务”中，避免后续两个入口出现行为不一致。

## 5. 服务职责设计

### 5.1 设备挂载管理

这一层不一定由 Python 服务直接完成，但服务需要感知挂载结果。

建议职责：

- 配置挂载根目录，例如 `/mnt/hyperspec` 或移动端应用可访问目录
- 检查目录是否存在、是否可读、是否可写入缓存结果
- 定期探测设备是否在线
- 当目录不可访问时，对前端输出“设备离线”状态

建议注意：

- Android 场景下更可能通过 OTG 或厂商目录同步方式挂载
- Linux 云端一般无法直接接 USB 移动设备，通常该服务更适合部署在边缘端、网关机、工控机、采集笔记本，或移动设备本地伴生服务中
- 如果前端部署在云端而设备在本地，推荐“采集接入服务在本地，业务 API 在云端”

### 5.2 目录监听服务

该服务持续监听挂载目录中的文件变化事件。

建议监听内容：

- 新建文件
- 文件重命名
- 文件内容变更
- 目录新增
- 目录删除

建议监听方式：

- 优先采用文件系统事件监听
- 在不稳定环境下增加兜底轮询扫描

原因：

- 单纯依赖事件监听，可能在某些挂载方式下丢事件
- 单纯依赖轮询，实时性差且资源浪费
- “事件触发 + 周期补偿扫描”通常最稳妥

### 5.3 文件就绪判定

这是方案中的关键点，必须单独设计。

问题在于：监听到“新文件出现”时，设备可能还在写入，直接处理容易读到半文件。

建议采用以下判定规则：

- 文件大小连续两次检测保持不变
- 文件最近修改时间在稳定窗口内不再变化
- 配套文件齐全后再开始处理
- 文件后缀符合白名单
- 文件名满足约定命名规则

例如：

- 若高光谱数据由 `.dat + .hdr` 组成，则必须成对出现
- 若设备写入一个批次目录，则以目录完整性作为处理触发条件

建议引入“稳定等待时间”，例如 2 到 5 秒，避免写入过程中的误触发。

### 5.4 任务编排服务

目录监听不应直接执行耗时推理，而应将任务交给编排器。

编排器职责：

- 为每个新样本创建唯一任务 ID
- 控制任务状态流转
- 防止同一文件重复处理
- 限制并发数量
- 记录处理耗时、异常信息、结果摘要

建议任务状态：

- `device_offline`
- `watching`
- `discovered`
- `waiting_stable`
- `queued`
- `processing`
- `success`
- `failed`
- `ignored`

其中 `ignored` 用于跳过临时文件、重复文件、格式不符文件。

### 5.5 预测处理服务

这里尽量复用当前已有逻辑，不新增第二套模型处理流程。

推荐改造方向：

- 将当前“从 `UploadFile` 读取”的流程，抽象为“从文件路径读取”与“从上传对象读取”两种输入适配
- 统一输出标准化的处理中间结果和预测结果
- 对新接入服务只暴露内部调用接口，不强依赖 HTTP 上传

目标是形成如下统一能力：

- 输入可以是上传文件
- 输入也可以是本地挂载目录中的文件路径
- 输出始终是统一的预测结果结构

### 5.6 前端接入方式

前端不再只负责上传文件，而是要展示设备和任务状态。

建议前端展示四类信息：

1. 设备状态
2. 目录监听状态
3. 最新任务列表
4. 单任务结果详情

推荐两种接入方式：

#### 方案 A：轮询接口

适合先快速落地。

前端周期请求：

- 当前设备是否在线
- 当前监听目录
- 最近 N 条任务记录
- 指定任务的结果详情

优点：

- 实现简单
- 调试成本低

缺点：

- 实时性一般
- 前端会产生重复请求

#### 方案 B：WebSocket 或 SSE

适合需要实时看到“新样本进入 -> 处理中 -> 完成”的场景。

推送事件可以包括：

- 设备已连接
- 设备已断开
- 发现新文件
- 文件稳定可处理
- 开始预测
- 预测成功
- 预测失败

建议：

- 初版可采用“REST 查询 + SSE/WS 推送状态”
- 如果团队更熟悉 HTTP 语义，可优先考虑 SSE

## 6. 推荐 API 设计

虽然当前阶段不落代码，但建议先定义接口边界。

### 6.1 设备状态接口

- `GET /api/device/status`

返回内容建议包含：

- 设备是否在线
- 挂载目录路径
- 目录是否可读
- 最近一次探测时间
- 当前监听状态

### 6.2 监听控制接口

- `POST /api/device/watch/start`
- `POST /api/device/watch/stop`

说明：

- 如果服务设计为启动即监听，这两个接口可以只保留状态查询
- 如果需要人工控制采集窗口，则保留启停接口更合适

### 6.3 任务列表接口

- `GET /api/device/tasks`

返回内容建议包含：

- 任务 ID
- 文件名
- 文件路径
- 发现时间
- 当前状态
- 错误信息
- 预测摘要

### 6.4 任务详情接口

- `GET /api/device/tasks/{task_id}`

返回内容建议包含：

- 任务基础信息
- 状态流转时间线
- 原始文件元信息
- 预测结果
- 异常原因

### 6.5 实时事件接口

- `GET /api/device/events`

可用于 SSE 或 WebSocket 推送。

## 7. 目录与模块建议

结合当前项目结构，建议未来新增如下模块，但当前阶段仅作为设计参考：

```text
backend/
├── app/
│   ├── routers/
│   │   └── device.py                # 设备状态、任务查询、监听控制接口
│   ├── services/
│   │   ├── device_watch_service.py  # 目录监听与事件采集
│   │   ├── device_task_service.py   # 任务编排与状态管理
│   │   ├── device_mount_service.py  # 挂载状态探测
│   │   └── prediction_service.py    # 统一封装上传/路径两种预测入口
│   ├── schemas/
│   │   └── device.py                # 设备状态、任务状态、事件消息模型
│   └── ...
└── runtime/
    ├── watch_cache/                 # 待处理缓存
    ├── processed/                   # 已处理归档
    └── failed/                      # 失败样本归档
```

其中关键原则是：

- 监听服务负责发现，不负责重计算
- 任务服务负责编排，不负责文件解析细节
- 预测服务负责统一调用现有算法能力

## 8. 状态机建议

为了便于前端展示和排障，建议明确任务状态机。

### 8.1 设备状态

- `offline`：未检测到挂载目录或目录不可访问
- `online`：目录可访问
- `watching`：已开始监听
- `error`：监听器异常或目录权限异常

### 8.2 文件任务状态

- `discovered`：发现新文件
- `waiting_stable`：等待文件写入完成
- `queued`：已进入处理队列
- `processing`：正在解析或推理
- `success`：预测成功
- `failed`：处理失败
- `ignored`：被规则跳过

### 8.3 前端展示建议

前端可以分三块显示：

- 顶部设备卡片：在线状态、目录路径、监听状态
- 中部任务流：最近采集文件与状态变化
- 底部结果区：成功样本的成分结果与可视化

## 9. 关键技术点与风险

### 9.1 USB 挂载稳定性

风险：

- 不同移动设备或系统对 USB 存储的挂载方式不同
- 某些环境只暴露 MTP，不暴露真实文件系统事件
- 云服务器通常无法直接访问本地 USB 外设

建议：

- 明确服务部署位置，优先部署在“能直接访问设备目录”的本地边缘侧
- 如果最终系统是“云端前端 + 本地设备”，考虑把该服务设计为边缘采集代理

### 9.2 文件写入未完成

风险：

- 设备正在写入时触发处理，导致解析失败

建议：

- 引入稳定检测窗口
- 支持失败后延迟重试

### 9.3 重复处理

风险：

- 监听事件重复触发
- 同一文件多次写入或重命名导致重复建任务

建议：

- 使用文件路径、文件大小、修改时间、内容摘要构成幂等键
- 记录已处理索引

### 9.4 大文件与性能压力

风险：

- 目录中积压大量历史样本
- 单次扫描耗时长
- 同时处理多个大文件导致内存占用高

建议：

- 初次启动时区分“历史补扫”和“新文件监听”
- 限制并发处理数
- 历史文件按时间窗口筛选

### 9.5 目录权限与安全

风险：

- 挂载目录无权限访问
- 恶意文件或非目标文件混入

建议：

- 限制监听目录范围
- 仅处理白名单后缀与命名规则
- 对异常文件独立归档

## 10. 部署建议

### 10.1 不推荐的部署方式

不建议把“USB 设备监听服务”直接部署在纯云服务器上，原因是云服务器通常无法直接感知本地手机或高光谱设备的 USB 挂载目录。

### 10.2 推荐部署方式

推荐以下两种部署形态：

#### 形态 A：边缘一体式部署

适用于：

- 高光谱设备连接到本地工控机、笔记本或边缘盒子
- 前后端都在本地或局域网访问

特点：

- 目录监听与预测服务都在本地
- 延迟低
- 调试简单

#### 形态 B：边缘采集代理 + 云端业务服务

适用于：

- 设备在本地
- 前端和主业务系统在云端

特点：

- 本地代理负责目录监听、文件稳定判定、预处理或上传
- 云端服务负责集中预测、结果管理、前端展示

这是更符合实际生产环境的方案。

## 11. 分阶段落地建议

建议分 4 个阶段推进。

### 阶段 1：验证链路可行性

目标：

- 验证高光谱设备是否能稳定以目录方式挂载
- 明确实际生成文件格式、命名规则、配套文件结构
- 确认移动设备或宿主系统能否感知文件变化

产出：

- 设备接入说明
- 挂载路径规则
- 样本文件规范

### 阶段 2：实现单机目录监听闭环

目标：

- 监听目录
- 识别新文件
- 文件稳定后自动调用现有预测逻辑
- 通过日志和任务列表输出结果

产出：

- 单机可运行的目录监听预测闭环

### 阶段 3：前端实时接入

目标：

- 前端展示设备状态与任务状态
- 支持轮询或 SSE/WS 查看最新预测结果

产出：

- 设备页或采集页
- 任务列表页
- 实时状态通道

### 阶段 4：增强稳定性与生产化

目标：

- 增加异常恢复
- 增加幂等处理
- 增加任务归档与告警
- 支持多目录或多设备

产出：

- 更稳定的生产版采集接入服务

## 12. 最小可行方案建议

如果希望先尽快验证，而不是一次做全，建议先做最小可行方案：

1. 固定一个挂载目录
2. 只监听 `.dat` 和必要配套文件
3. 用“文件大小稳定 3 秒”作为就绪条件
4. 发现新样本后复用现有预测能力
5. 将结果写入任务列表
6. 前端先通过轮询获取任务状态

这样可以最低成本验证：

- 设备目录监听是否可靠
- 文件格式是否稳定
- 从采集到预测的整链路是否可用

## 13. 对当前项目的具体建议

结合当前后端代码结构，建议优先做以下架构调整，再开始编码：

1. 将当前上传预测流程抽象为“统一预测服务”
2. 新增“设备状态”和“任务状态”的数据模型
3. 明确监听服务是内嵌在 FastAPI 生命周期中，还是独立进程运行
4. 明确前端实时通信采用轮询、SSE，还是 WebSocket
5. 明确部署位置是在本地边缘端还是云端

其中最关键的问题不是代码，而是部署拓扑：

- 如果 USB 设备连接在本地，服务就应靠近设备部署
- 如果系统主体在云端，推荐本地代理 + 云端业务服务的双层结构

## 14. 结论

你的思路整体可行，但前提是“高光谱设备的数据能够以目录方式稳定挂载并被宿主系统访问”。

从工程实现角度，最合理的方案不是直接修改现有上传接口，而是：

- 在现有预测能力之前增加一个目录监听接入层
- 用任务编排隔离“文件发现”和“模型处理”
- 用状态接口或实时推送将处理过程接给前端
- 优先部署在靠近 USB 设备的边缘侧环境

如果后续开始落地代码，建议优先完成：

1. 部署形态确认
2. 文件格式与挂载方式确认
3. 统一预测服务抽象
4. 目录监听闭环
5. 前端状态接入
